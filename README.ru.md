# Очистка базы Медок (M.E.Doc): уменьшить ZVIT.FDB и освободить место на диске

[English](README.md) · [Українська](README.uk.md) · **Русский**

База **Медок (M.E.Doc)** `ZVIT.FDB` разрослась до десятков гигабайт, а встроенная
архивация (Администрирование → Архивирование документов) работает по 15–30 секунд на
один документ? Здесь скрипты и заметки о том, как **удалить старые первичные
документы прямо из базы Firebird** и **физически вернуть место на диске**, которое
Firebird сам никогда не отдаёт после `DELETE`.

Инструмент сделан по итогам реальной очистки, где штатная архивация Медок оказалась
слишком медленной. Все данные компаний убраны, пути и пароли вынесены в параметры.
**Каждый скрипт нужно прочитать и адаптировать под себя, а не запускать вслепую на
своей базе.**

> **Удаление необратимо.** Отменить шаг `DELETE` можно только восстановлением из
> резервной копии. Сделайте полную копию, проверьте, что она восстанавливается, и по
> возможности сначала протестируйте на копии базы, а не на рабочей.

## Быстрый старт

1. Сделайте резервную копию и проверьте её: `scripts/1-backup-database.ps1`.
2. Узнайте код вашей организации: `select code, edrpou from org order by code;`
3. Найдите таблицу `<форма>_main` и поле даты нужной формы (см. ниже).
4. Сгенерируйте SQL с удалением по месяцам, просмотрите и только потом запускайте:
   `scripts/generate-batch-delete-sql.ps1`.
5. Верните место на диске: `1-backup` → `2-restore` → `3-swap`.
   Простой нужен только на шаге 3.

## Что внутри

- `scripts/generate-batch-delete-sql.ps1`: генерирует SQL, который по месяцам
  удаляет документы заданной формы, периода и организации из `CARD` и каскада.
- `scripts/1-backup-database.ps1`: шаг 1 из 3, онлайн-копия `gbak`.
- `scripts/2-restore-database.ps1`: шаг 2 из 3, онлайн-восстановление в новый файл
  (именно это сжимает базу: свежий restore не содержит «мусора» от удалённых строк).
- `scripts/3-swap-database.ps1`: шаг 3 из 3, единственный с простоем; подменяет
  файл сжатой базой.

## Почему после DELETE файл базы не уменьшается

Firebird работает на MVCC и не возвращает страницы ОС после `DELETE`: файл `.FDB`
только растёт или остаётся прежним, пока вы не сделаете backup/restore, который
переписывает базу в новый файл без пустого места. Сами `DELETE` на размер файла не
влияют, они уменьшают число строк и стоимость запросов. Место на диске возвращает
именно backup/restore.

## Почему не встроенная архивация Медок

Архивация в интерфейсе Медок удаляет каждый документ на уровне приложения, в тяжёлых
последовательных запросах (включая полное сканирование самой большой таблицы строк
документов) в одной длинной транзакции. На базе с большим числом документов это
становится непригодным (наблюдалось 15–30+ секунд *на документ*) и не справляется с
многолетним завалом. Кроме того, в некоторых версиях на больших периодах бывает
`System.ArgumentException: Column 'PARENTDOCID' does not belong to table DOCRST`.

Если вам действительно нужен архивный файл, который создаёт эта функция (например,
для требований учёта), этот инструмент **его не заменяет**: он удаляет строки без
какого-либо архива. Используйте, только если вы твёрдо уверены, что архивная копия
удаляемого вам не нужна.

## Заметки о схеме (Медок / Firebird, проверяйте на своей версии)

Это факты, которые пришлось выяснять, изучая схему. Они подтвердились для Medoc
11.02.x на Firebird 3.0.5 Classic, но сверьтесь со своей установкой (`RDB$TRIGGERS`,
`RDB$RELATION_CONSTRAINTS` и т. д.):

- **`CARD`** — центральная строка каждого документа любого типа (отчётность,
  налоговые накладные, расчёты корректировки и т. д.). Первичный ключ `CODE`.
- У каждого *типа* документа своя таблица `_MAIN` (часто и `_TAB1` и др.), связанная
  через `<form>_main.CARDCODE = CARD.CODE`. **Название поля даты в разных формах
  разное:** не угадывайте `DATE`, `N1` или другое, ищите для каждой формы.
- `RDCARD` / `RDCARD_HISTORY` заполняются только для части типов документов;
  `RDCARD_HISTORY` фиксирует то, что прошло через *официальную* архивацию
  (`ARCH_IDENT` = имя архивного файла), а не наличие документа.
- Удаление строки `CARD` запускает:
  - триггер `BEFORE DELETE`, явно чистящий около 100 сопутствующих таблиц (журналы,
    подписи, сертификаты, изображения, маршрутизацию, метки, форм-специфичные
    таблицы). Проверьте тело триггера в `RDB$TRIGGERS` на своей версии;
  - триггер `AFTER DELETE`, чистящий блоб-хранилище документа;
  - несколько сотен внешних ключей `FOREIGN KEY ... ON DELETE CASCADE` для таблиц
    `_MAIN`/`_TAB1` всех форм отчётности;
  - **один найденный пробел:** `CARDJOURNALOPERBLOB` (через `CARDJOURNALOPER.CODE`)
    не имеет каскада и чистится вручную перед удалением `CARD`. Скрипт генерации
    делает это по умолчанию. На другой версии могут быть и другие пробелы:
    проверьте сами.
- База часто **мультиорганизационная**: в одной базе Firebird несколько компаний
  (таблица `ORG`), их различает `CARD.IDORG`. **Всегда** ограничивайте удаление по
  `idorg`: сначала выполните `select code, edrpou from org order by code;`.
- Кодировка текста на старых установках обычно WIN1251. При чтении значений через
  PowerShell используйте `[System.Text.Encoding]::GetEncoding(1251)`. `isql` в
  POSIX-оболочке (git-bash) может показать «кракозябры», но числа и даты
  сравниваются корректно.

### Как вручную найти документ

Когда известны таблица `_MAIN` формы и поле даты:

```sql
select fj.cardcode, fj.<поле_номера> as num, fj.<поле_даты> as docdate, fj.edrpou
from <форма>_main fj join card c on c.code = fj.cardcode
where fj.<поле_номера> = '<номер документа>' and fj.edrpou = '<ЕДРПОУ контрагента>';
```

Имена полей узнайте через `FORM.CHARCODE` (`select code, charcode from form order
by charcode;`) и по строке известного живого документа.

## Метод пакетного удаления

**Никогда не удаляйте многолетний диапазон одной транзакцией:** это та же проблема
накопления мусора MVCC, что и у штатного архиватора, только через SQL. Всегда
разбивайте по месяцам с `COMMIT` после каждого.

`scripts/generate-batch-delete-sql.ps1` генерирует именно такой шаблон. Один блок:

```sql
select '<год>-<месяц>: ', count(*) as to_delete
from <main_table> fj join card c on c.code = fj.cardcode
where c.idorg = <idorg> and fj.<date_field> between '<год>-<месяц>-01' and '<год>-<месяц>-<последний_день>';

delete from cardjournaloperblob where code in (
  select j.code from cardjournaloper j where j.cardcode in (
    select fj.cardcode from <main_table> fj join card c on c.code = fj.cardcode
    where c.idorg = <idorg> and fj.<date_field> between '<год>-<месяц>-01' and '<год>-<месяц>-<последний_день>'
  )
);

delete from card where code in (
  select fj.cardcode from <main_table> fj join card c on c.code = fj.cardcode
  where c.idorg = <idorg> and fj.<date_field> between '<год>-<месяц>-01' and '<год>-<месяц>-<последний_день>'
);

commit;
```

Сгенерируйте и запустите (значения иллюстративные, подставьте свою таблицу `_main`,
поле даты, код организации и годы):

```powershell
.\scripts\generate-batch-delete-sql.ps1 -MainTable <form>_main -DateField <date_field> `
    -IdOrg <your_idorg> -YearStart <year_from> -YearEnd <year_to> -OutFile .\delete.sql
```

```bash
isql.exe -user SYSDBA -password <your_password> "localhost/3050:C:\path\to\db.FDB" -i delete.sql -q > output.txt
```

**Проверка после:** просуммируйте `to_delete` по месяцам и сравните со свежим
`count(*)` по всему диапазону: должно быть 0 (или то, что вы сознательно оставили),
а сумма должна совпадать с тем, что вы видели в превью до запуска.

## Backup / restore / swap: физический возврат места на диске

Выполняйте по порядку; между шагами 1–2 и шагом 3 может быть любая пауза
(например, шаги 1–2 днём, шаг 3 в окно обслуживания):

1. **`scripts/1-backup-database.ps1`**: ненадолго останавливает службу приложения
   (чтобы не копировать посреди записи), запускает `gbak -b` с прогрессом (размер
   файла, % от источника, последняя таблица) и снова запускает службу. Служба
   Firebird всё время работает, живой файл базы не трогается.
2. **`scripts/2-restore-database.ps1`**: восстанавливает копию в **новый отдельный
   файл**, желательно на другом физическом диске, если места мало. Полностью
   онлайн: ничего не останавливается. Это медленный шаг (для нескольких ГБ нормально
   больше часа), но без простоя.
3. **`scripts/3-swap-database.ps1`**: **единственный шаг с простоем.** Останавливает
   Firebird и приложение, переименовывает текущий файл в сторону (не удаляет),
   копирует новую сжатую базу, проверяет совпадение размера, удаляет источник
   restore, запускает службы и (по желанию) выполняет проверочный запрос.

### Известные проблемы

- **Файл заблокирован при swap (Firebird Classic Server):** `Stop-Service` не всегда
  завершает рабочие процессы `firebird.exe`, которые Classic порождает на каждое
  соединение, и копирование падает с `IOException`. Решение: найти и завершить
  оставшиеся процессы `firebird.exe` и запустить скрипт ещё раз (он идемпотентен).
- **Прогресс копирования прыгает до 100% в начале:** NTFS мгновенно резервирует
  полный размер файла, поэтому «copied X / Y (100%)» может появиться задолго до
  реального завершения. Это не сбой и не зависание: скрипт дожидается завершения и
  проверяет итоговый размер.
- Шаг 3 намеренно ничего не удаляет из старой базы. Убедитесь, что приложение
  корректно работает с новой базой, и только потом сами удалите
  `<name>_before_restore_<timestamp>.FDB` и промежуточный `.FBK`.

## Альтернатива: собственный BackupManager Медок

В Медок есть `BackupManager.exe` (в каталоге установки и в меню программы): полный
«холодный» backup/restore одним шагом, результат в файле `.BKZ`:

- **Резервное копирование** («Створити архів») останавливает и службу приложения, и
  службу Firebird на всё время; прогресс показывается в объектах/блоках, а не в
  байтах. Полезно включить «Створювати архів з перевіркою бази» и лимит числа копий.
- **Восстановление** («Відновити з архіву») тоже холодное, но надёжное: остановить
  службы → убедиться, что нет оставшихся `firebird.exe` → отодвинуть живой файл →
  указать `.BKZ` → дать приложению поднять службы → проверить простым запросом.

Оба пути приводят к рабочему результату. `gbak`-скрипты не останавливают Firebird во
время медленного backup; `BackupManager` проще и «официальнее», но даёт больший
простой.

## Отказ от ответственности

Это описание одной конкретной очистки, обобщённое в скрипты, а не официальный
инструмент Медок. Детали схемы (названия таблиц, поведение триггеров, покрытие
каскадов) различаются между версиями: проверьте каждое допущение на своей
установке (`RDB$TRIGGERS`, `RDB$RELATION_CONSTRAINTS`, `COUNT(*)` с ограничением
перед любым удалением). Всегда сначала делайте резервную копию.
